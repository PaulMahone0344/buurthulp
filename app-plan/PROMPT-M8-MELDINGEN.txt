VASTE KEUZES
1. TWEE LAGEN. Laag 1 (nu bouwen): meldingen IN de app, via een nieuwe
   collectie hh_meldingen + realtime. Laag 2 (echte push naar het
   toestel via Firebase/APNs) vraagt een Firebase-project, een
   Apple-sleutel en een verzender die RS256 kan tekenen; de
   PocketBase-JSVM kan dat niet zelf. NIET bouwen. Wel voorbereiden:
   een interface PushRegistratie (registreerToken/verwijderToken) met
   een lege implementatie, en de opslag in hh_push_tokens achter de
   gateway, zodat laag 2 later alleen de implementatie wisselt. Zet in
   OPEN-PUNTEN-M8 wat laag 2 nodig heeft en dat "klaar als: komt aan op
   toestel" uit het plan daarmee nog openstaat.
2. hh_meldingen (script 30): ontvanger (hh_users, verplicht, verdwijnt
   mee), soort (keuze: nieuwe_klus | toegewezen | onderweg | afgerond |
   geannuleerd | incident), klus (verwijzing, mag leeg), incident
   (verwijzing, mag leeg), titel, tekst, gelezen_op (datum). Index
   ontvanger. Rules (31): lezen = ontvanger; bijwerken = ontvanger,
   alleen gelezen_op (hook zet elk ander veld terug, zie ObyCom);
   aanmaken/verwijderen = niemand via de API (hook schrijft via $app).
3. TRIGGERS in jouw hook, op onRecordAfterCreateSuccess van
   hh_klus_status (M6 schrijft daar elke wissel, ook bij accepteren):
   naar geaccepteerd -> melding aan de oudere (en geplaatst_door als
   dat iemand anders is); naar onderweg -> oudere; naar afgerond ->
   oudere en jongere; naar geannuleerd -> de andere deelnemer; terug
   naar open na annuleren door de jongere -> oudere. Nieuwe open klus
   -> goedgekeurde jongeren in dezelfde wijk (max 50 ontvangers).
   Idempotent: (ontvanger + soort + klus + logregel) nooit dubbel.
   Een fout in een trigger mag NOOIT de statuswissel breken
   (try/catch + log). Teksten in gewone taal, voor de oudere met u.
4. INCIDENT (O11): aanmaken via de gewone API (createRule bestaat).
   De hook maakt bij elk nieuw hh_incidenten-record een melding soort
   incident voor ELKE coordinator. Bij soort nood ook een melding aan
   het gekoppelde familielid als die er is. M10 toont ze.
5. BEL ONS (O10): een knop die het meldkamernummer belt (url_launcher,
   tel:). Nummer komt uit een constante in een eigen config-bestand
   lib/features/hulpvrager/veiligheid/meldkamer_config.dart met een
   duidelijke PLACEHOLDER; open punt: echt nummer van Mozaiek.
   Koppel de bestaande O1-knop "Bel ons" hieraan.

APP
  Meldingen-overzicht per rol (/meldingen): lijst, ongelezen-stip,
      tik -> bijbehorende klus, gelezen_op zetten. Belletje met
      ongelezen-teller in de kop van jongere, familie en coordinator.
      Voor de OUDERE geen teller en geen lijst: de laatste melding staat
      als een rustige regel bovenaan O1 ("Sanne komt morgen om 10 uur").
  O10 Bel ons: een scherm, een grote knop, openingstijden-regel
      (placeholder-tekst in teksten-bestand).
  O11 Probleem melden / noodknop: twee grote knoppen. "Ik heb nu hulp
      nodig" -> bevestigvraag -> incident soort nood (zonder klus mag)
      -> scherm "We bellen u zo snel mogelijk" + knop Bel ons.
      "Er is iets niet goed gegaan" -> drie vaste keuzes + anders ->
      incident soort probleem, met de lopende klus erbij als die er is.
      Jongere krijgt dezelfde "Probleem melden"-ingang op J15 (ook bij
      status bezig; M6 liet annuleren daar bewust weg).
  Realtime: subscribe op hh_meldingen van de ingelogde gebruiker.
  Gateway: meldingen_gateway.dart, incident_gateway.dart + fakes.
  Tests: unit (teksten per soort en rol), widget (overzicht, O10, O11
  beide dichtheden 200 procent, semantiek, max drie keuzes), flow met
  fake (nood melden, probleem met klus, melding komt binnen via stream,
  gelezen zetten, oudere ziet regel op O1).
